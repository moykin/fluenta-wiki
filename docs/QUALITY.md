# Стандарты качества и производительности

> Живой документ. Обновлять при изменении бюджетов и порогов. Обновлено: **2026-07-31**.

Принцип: всё, что можно проверить машиной, проверяет машина. Ревью — для того, чего линтер не увидит.

## Автоматические гейты

| Когда | Что проверяется | Чем |
|---|---|---|
| До коммита | секреты, приватные ключи, крупные файлы, формат | pre-commit + gitleaks |
| В PR | формат, линт, типы, тесты, сборка всех трёх частей | `ci.yml` |
| В PR | производительность и SEO маркетинга | Lighthouse CI |
| В PR и еженедельно | утёкшие секреты, CodeQL, уязвимые зависимости, конфигурация | `security.yml` |
| При деплое | уязвимости в собранном образе | Trivy (критические ломают выкатку) |

Локально ровно то же — `make check`. Расхождений между «у меня работает» и CI быть не должно.

## Код

**Python:** `ruff` для формата и линта, `mypy` в строгом режиме. Типы обязательны в сигнатурах. Конфигурация — только через переменные окружения, никаких значений в коде.

**Dart:** `dart format`, `flutter analyze --fatal-infos`. Строгие правила анализатора включаются в `analysis_options.yaml` при создании проекта: `strict-casts`, `strict-raw-types`.

**Клиент API не пишется руками.** FastAPI отдаёт OpenAPI-схему, из неё генерируется Dart-клиент. Один источник правды — рассинхронизация типов между фронтом и бэком становится невозможной.

**Миграции — только через Alembic.** Ручные `ALTER TABLE` на сервере запрещены: расхождение схемы между dev и прод обнаруживается в самый неудобный момент.

## Тесты

| Слой | Что покрываем |
|---|---|
| Unit (backend) | учёт минут, гейтинг тарифов, FSRS-планирование, парсинг разбора |
| Unit + widget (Flutter) | логика экранов, состояния, адаптивные лэйауты |
| Golden | ключевые экраны против дизайна — защита от «поехало и никто не заметил» |
| Integration | онбординг целиком, сессия тьютора, цикл повторений |

Порог покрытия backend — 70%, ломает CI. Смысл не в проценте, а в том, чтобы критичная логика не осталась вовсе непокрытой.

**Что покрывать обязательно, независимо от процента:** всё, что связано с деньгами и лимитами. Списание голосовых минут, гейтинг Free/Pro, покупка пакетов. Ошибка здесь — это либо потерянные деньги, либо обманутый пользователь.

## Бюджеты производительности

**Маркетинг и SEO** (проверяется Lighthouse CI в каждом PR):

| Метрика | Порог |
|---|---|
| Lighthouse Performance | ≥ 90 |
| Lighthouse SEO | 100 |
| Lighthouse Accessibility | ≥ 95 |
| LCP | < 2.5 с |
| CLS | < 0.1 |
| TBT | < 200 мс |
| Вес страницы | < 400 КБ |

Core Web Vitals влияют на ранжирование, а SEO — основной канал привлечения. Поэтому это не пожелания, а ломающие сборку пороги.

**API:**

| Метрика | Порог |
|---|---|
| p95 обычных запросов | < 200 мс |
| p95 запросов с LLM-разбором | < 2.5 с (иначе показывать прогресс) |
| Время до первого звука ответа тьютора | < 800 мс |

Последнее — про ощущение живого разговора. Пауза дольше секунды читается как «сломалось», а не как «думает». Сюда же входит сетевая задержка до Орегона, поэтому цифру нужно проверять из EU, а не с локальной машины.

**Приложение:**

- Скролл читалки — 60 fps на среднем устройстве, без пропущенных кадров при подсветке слов.
- Тап по слову → перевод: мгновенно, без индикатора загрузки (для того и локальный перевод).
- Холодный старт до первого экрана — < 2 с.

## Доступность

Дизайн это уже учитывает, реализация не должна терять:

- Тач-цели ≥ 44px.
- Уважать `prefers-reduced-motion`.
- Контраст текста не ниже AA.
- Dyslexia-friendly режим и TTS — часть продукта, а не опция «когда-нибудь».
- Приложение должно быть проходимо с клавиатуры и понятно скринридеру.

## Наблюдаемость

- Структурные логи (JSON), с идентификатором запроса.
- Отдельно логировать **задержку и стоимость каждого вызова LLM** — это одновременно метрика качества продукта и статья расходов. Без этого нельзя ответить на вопрос «почему счёт вырос».
- Метрики использования голосовых минут — на них завязана монетизация.
- Ошибки клиента собирать с обеих платформ, а не только с сервера.

## Процесс

- **Маленькие PR.** Один PR — одно изменение. Ревью на 800 строк не бывает ревью.
- **`main` всегда рабочая.** Всё, что в ней, готово к выкатке.
- **Крупные технические решения** записываются в [ARCHITECTURE.md](ARCHITECTURE.md) вместе с причиной. Через полгода причина забудется, и решение будет выглядеть произвольным.
- **Зависимости обновляются еженедельно** (Dependabot, сгруппированные PR). Редкие большие обновления болезненнее частых маленьких.
