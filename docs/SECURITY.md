# Правила безопасности (публичный репозиторий)

Репозиторий Fluenta **ПУБЛИЧНЫЙ**. Никакие ключи, секреты и личные данные не должны попадать в код, коммиты или историю.

**Почему это критично:** утечка секрета в публичный репо = мгновенная компрометация (боты сканируют GitHub за секунды); git-история хранит секрет **навсегда**, даже после удаления из файла — приходится ротировать ключ. Личные данные (email, продовые IP, имена) в публичном репо — это приватность и лишняя attack surface.

## Что НИКОГДА не коммитить

- API-ключи (Gemini, OpenAI, любые LLM), пароли БД, JWT / session secrets.
- Приватные SSH-ключи (напр. `~/.ssh/fluenta_hetzner`), OAuth client secrets, токены.
- `.env` с реальными значениями, продовые IP / хосты, персональные email.
- Инфраструктурные детали → держим в `INFRA.local.md` (gitignored).

## Как обращаться с секретами

- **Только через env:** реальные значения в `.env` (в `.gitignore`); в репо — лишь `.env.example` с плейсхолдерами.
- На сервере — через `env_file` docker-compose (не в репо) или secret manager.
- IaC/провижн-секреты вне репо; если IaC коммитится — шифровать (SOPS / Ansible Vault / age).

## `.gitignore` обязан покрывать

`.env`, `.env.*` (кроме `.env.example`), `*.pem`, `*.key`, `id_*`, `*_rsa`, `*_ed25519`, `secrets/`, `credentials*`, `*.p12`, `*.local.md`, `*.local`, `node_modules/`, build-артефакты.

## Сканер секретов (обязательно)

- Поставить **gitleaks** (или trufflehog / git-secrets) как **pre-commit hook** + в CI — чтобы секрет физически не мог уйти в коммит.

## Если секрет всё же закоммичен

1. **Сразу ротировать** (сгенерировать новый ключ/пароль) — не полагаться на удаление из истории.
2. При необходимости чистить историю (`git filter-repo`), но ротация первична.

## Прочее

- README / доки / скриншоты — без реальных креды, токенов, продовых IP.
- Коммиты подписывать (GPG / SSH signing) желательно.
- Не светить приватный email — использовать GitHub noreply email.

# Операционная безопасность

> Раздел добавлен 2026-07-31 вместе с контуром CI/CD.

Принцип: безопасность держится на автоматике, а не на дисциплине. То, что зависит от «не забыть», рано или поздно забывается.

## Что уже работает автоматически

| Рубеж | Что делает |
|---|---|
| pre-commit | gitleaks, поиск приватных ключей, блокировка крупных файлов — секрет не может попасть даже в локальный коммит |
| CI на каждый PR | gitleaks по всей истории, CodeQL, OSV-scanner, Trivy (уязвимости, секреты, конфигурация) |
| Еженедельно | те же проверки по расписанию — уязвимости появляются и в уже написанном коде |
| При деплое | Trivy по собранному образу; критические уязвимости останавливают выкатку |
| Dependabot | еженедельные обновления зависимостей и самих GitHub Actions |

Установка на новой машине — `make hooks`. Разовая проверка — `make secrets`.

## Сервер

Настраивается скриптом `infra/provision.sh`:

- Вход только по SSH-ключу, root-логин запрещён, пароли отключены, `MaxAuthTries 3`.
- UFW: входящие запрещены, кроме 22 / 80 / 443.
- fail2ban на sshd.
- Автоматические обновления безопасности.
- ⚠️ **Docker публикует порты в обход UFW.** Поэтому наружу смотрит только Caddy. Postgres не объявляет `ports:` вообще и живёт во внутренней сети без выхода в интернет.
- Контейнеры: `no-new-privileges`, `cap_drop: ALL`, лимиты памяти, ограниченные логи.

## Приложение

- **Учёт минут и гейтинг тарифов — только на сервере.** Клиент можно подменить; любое ограничение, проверяемое на клиенте, не является ограничением.
- Ключ Gemini живёт **только** на сервере. Клиент общается с релеем, а не с Google напрямую.
- JWT: короткий срок жизни access-токена, ротация refresh-токенов. Пароли — argon2.
- Rate limiting на аутентификации и на дорогих LLM-эндпоинтах (защита и от перебора, и от выжигания бюджета).
- Строгий CORS: списком доменов, без `*`.
- Security-заголовки на Caddy: HSTS с preload, `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, `Permissions-Policy` (микрофон — только своему источнику).
- Валидация входных данных через Pydantic; запросы к БД только через ORM.

## Данные пользователей

Продукт работает с голосом, а это персональные данные:

- **Запись пересказа по умолчанию не хранится** — остаются только выделенные ошибки. Это одновременно продуктовое и защитное решение: чего нет на диске, то не утечёт.
- Хранение включается пользователем осознанно, тумблером, и должно быть отключаемо в любой момент.
- Удаление аккаунта должно удалять записи и производные данные, а не помечать флагом.
- Бэкапы шифровать; срок хранения — ограниченный.
- В логи не должны попадать тексты пересказов, содержимое личных импортированных текстов и токены.

## Ветка `main`

- Прямой push запрещён, изменения только через PR.
- Обязательные проверки: CI и Security.
- Force-push и удаление ветки запрещены.
- Прод-окружение требует ручного подтверждения на выкатку.

## Раз в квартал

1. Ротация: `JWT_SECRET`, ключи Gemini, ключ деплоя.
2. Проверка, что восстановление из бэкапа реально работает.
3. Просмотр открытых портов и правил файрвола Hetzner.
4. Обновление базового образа и Ubuntu.

## Если секрет всё же утёк

1. **Немедленно ротировать** — удаление из истории вторично, ключ уже мог быть прочитан ботами.
2. Проверить логи на использование скомпрометированного ключа.
3. Только потом чистить историю (`git filter-repo`).
